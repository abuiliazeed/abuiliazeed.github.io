The Repository Nobody Reviews

On Wednesday, Amazon shipped a developer tool that emulates more than 200 AWS services on your own machine. It is free, written in Rust, updated continuously — hundreds of agents fix thousands of issues in it every day — and its source sits on GitHub under a license that lets anyone do anything with it. The team responsible for it has not written or reviewed a single line of its code.

“The emulator was written entirely by autonomous agents,” Matt Goldberg, the AWS senior principal engineer behind the project, wrote in the launch post. “Our team hasn’t written or reviewed any of the code.” Amazon is touting that as a selling point, and it is getting attention — but mostly for the wrong reason. This is not a milestone in code generation; every lab can demo code generation. It is the first time a hyperscaler has shipped, and committed to indefinitely maintain, a product whose repository is run end to end by agents, with humans employed exclusively to build the system that keeps them honest.

Most people think the hard problem in agent-first development is getting agents to write good code. AWS Emulator is evidence that the hard problem is manufacturing trust without a human ever opening the diff. Solve that, and the code writes itself — continuously, at zero marginal engineering cost.

What Actually Shipped

AWS Emulator is a local program that serves an AWS API endpoint on your machine. You install it from a package on Linux or run it in Docker on macOS and Windows, point the AWS CLI or any SDK at localhost through a few environment variables, and your code runs unchanged: queues get created, tables get written, messages get acknowledged — no AWS account, no network, no deployment. Because it is built from the same public API models the SDKs use, the requests you send and the errors you get back have the same shape as the cloud’s. There is no service fee; you pay AWS only when you actually deploy.

Amazon’s motivation, laid out candidly across the launch posts, is that coding agents broke testing. An agent verifies its work by running the code and reading the result — then running it again, dozens of times per task. Point that loop at real AWS and every iteration buys latency and a line on a bill. Agents now write code faster than teams can test against the real cloud, so AWS moved the cloud to the agent.

The origin is a weekend experiment. Goldberg, inspired by Anthropic’s earlier demonstration of Claude agents building a C compiler, gave Kiro a three-step prompt describing his idea: here is how a service should behave, here is the real service to check against. Fifteen minutes later he had a passable first version of an SQS emulator. Everyone quotes the fifteen minutes. The actual invention is everything between that prototype and a maintained product spanning more than 400 API models.

Three Teams and a Gate

The emulator is kept alive by an organization of agents divided into three teams — divided, AWS says, because agents succeed on bounded tasks. The first team writes fidelity tests: real-world scenarios derived from the public API models, each of which must first be verified against real AWS before it counts. A test records how the cloud actually behaves, not how an agent guesses it behaves. There are tens of thousands of them, and the suite keeps growing as agents discover more of what AWS can do.

The second team replays those tests against the emulator, hunts for divergence, and files an issue for every failure, grouping failures that might share a root cause. When the system bootstrapped the repository, it generated an empty web server that could route requests for 438 API models but did nothing; the first issues of its life were as blunt as “build a first version of Amazon SQS.” The third team is fixers: one agent per issue, checking out the code, root-causing, editing until the issue is addressed.

Then every change meets the merge gate, and the gate is where the design lives. It blocks anything that doesn’t compile. Other agents review the change against coding standards. Security agents attack it adversarially — twice: once while the fix is being made, and again in the release pipeline before anything ships. The fidelity suite replays to prove the change didn’t regress accuracy. Fail any check and the change goes back for rework; pass everything and it merges to mainline. Hundreds of agents run this loop concurrently — on Bedrock AgentCore, CodePipeline and CodeCommit — fixing thousands of issues a day. No human reviews their output. Humans designed the game; agents play it.

Why This Works Where Your Agent Repository Doesn’t

Nothing in this system requires secret models. The ingredients are almost embarrassingly ordinary, and that is the lesson. A spec that already existed: AWS services are described in public, machine-readable API models, so “correct behavior” was written down years before any agent arrived. An oracle that cannot be persuaded: real AWS, which answers every fidelity question the same way no matter what the agent believes or argues. And a mechanical gate between agent output and mainline that no amount of fluent explanation gets through.

Compare that with how most teams run agents. Last week I covered the benchmark finding that when a coding agent reports a clean “done,” external verification fails 57% of the time. Agents are poor judges of their own open-ended work. A new benchmark of 100 expert-authored engineering tasks, published this week, hit the same wall from another angle: seven frontier models, five runs each, and on 80 of the 100 tasks not a single model earned full credit on every run. Wherever the grader is the agent’s own judgment, the scores cap out. AWS didn’t teach its agents to judge better. It removed judgment from the loop wherever a machine could check the answer instead.

The fidelity bar is brutal in exactly the right way. A test passes only if the emulator matches AWS on the response to every call — status code, body, exact error code and message — and on the data the workflow creates. Not “similar.” Not “functionally equivalent.” Identical. That is what turns a swarm of unverifiable writers into a workforce you can leave alone in a codebase indefinitely.

What about the work that has no oracle — product taste, architecture, naming, strategy? That stays human, and the boundary is finally legible: agents get everything that can be checked; humans keep everything that can only be judged. The mistake to avoid is pretending judgment work has an oracle when it doesn’t. Bolting a bogus metric onto taste just trains your agents to satisfy the metric. AWS had it easy: its ground truth existed for a decade. Most teams will have to manufacture the ground truth first, and that — not prompt engineering — is where the next year of agent work actually lives.

The Job Is the Guardrails Now

Werner Vogels, AWS’s longtime CTO, published his own essay alongside the launch, connecting the emulator to the simulation-first distributed-systems work from earlier in his career, and he stated the new job description plainly: when agents write the code and check their own work, the engineer’s job is to build the specs, tests, and merge gates that decide when that work is correct.

His anecdote prices the lesson. Years ago, he and a colleague spent about four months building the replication engine for a storage system. He recently rebuilt it with Kiro — and supervised the agent for four nights before noticing the real problem: it had no way to check its results. Once it had a spec and a test environment, the rebuild took about two hours. Everyone quotes the two hours. The expensive parts were the four months of system knowledge and the four nights he lost learning that an agent without an oracle just wanders.

This is the discipline at the center of Harness Engineering: The Complete Guide to Agent-First Software Development — the model is one component of a system whose levers, environment and verification shape outcomes as much as weights do. The engineers who internalize this stop asking “which model writes the best code” and start asking “what is the cheapest machine that can prove the code wrong.” Amazon just built that question into a product, then handed the product away for free because the moat was never in the code.

Read the Fine Print

The emulator has real limits, and Amazon is unusually direct about them. It does not simulate throttling, outages, or regional differences in which services are available. It does not evaluate IAM policies the way AWS does — a request the real cloud would deny can succeed locally — so it is explicitly not a security test. Its backlog of known gaps ships in a public GitHub folder unironically named “things-that-do-not-work.”

Keep your skeptic’s hat on, too: “100% agent-written” is also a marketing story from the company selling the agent platform it runs on, and the fidelity numbers are Amazon’s own. But the unusual part is that the claim is checkable. The source is public under CC0, the method is documented, and the failures ship with the repository. Most “our agents built this” claims cannot be audited. This one invites you to try.

What to Do This Week

If you build on AWS, move your agents’ verify loop off the cloud. Install the emulator — you need AWS CLI 2.35 or newer, and there is an official aws-emulator skill so your coding agent can wire the whole thing up itself — then point your tests at the local endpoint and measure what happens to iteration speed and CI spend when run-check-run stops paying cloud latency and cloud prices.

If you don’t, steal the pattern anyway; it needs no Bedrock. Pick one repository you own and ask the only question that matters: what is the “real AWS” for this code — the thing that answers correctly regardless of what the agent believes? A production API. A schema. A ledger. A legacy system. Then assemble the same three parts: write down the spec that already exists, generate tests verified against that production source of truth, and put a mechanical gate in front of mainline that evidence — not persuasion — gets you through.

Re-budget your own hours accordingly. Every hour spent converting a human judgment call into a mechanical check is an hour that compounds. Every hour spent reviewing agent code by hand is an hour competing with teams whose repositories review themselves. The scarcest engineering resource in 2026 is not attention to code. It is ground truth.

The question that used to decide careers — can agents write production code? — is settling. The sharper question this launch raises is: in your market, who owns the oracle? Amazon just demonstrated that when the source of truth is public, mechanical, and wired into the gate, a codebase nobody reads can become the most reliably maintained software a company ships. The durable asset is no longer the code. It is the system that proves the code is right.
