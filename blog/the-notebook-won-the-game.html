The Notebook Won the Game

605 deaths. 22% of all programs ended in an error. Six server crashes mid-run. And at the end of it, the dragon was dead. Last week, a Google DeepMind team dropped four Gemini 4 Argon agents into a randomly generated Minecraft survival world with one paragraph of instructions — the objective is to defeat the Ender Dragon, any means within the rules of survival mode is permitted, the players decide how to share the work — and gave them nothing else. No roles, no game logic, no human input. Twenty-seven hours and fourteen minutes later, after writing and running 2,783 JavaScript programs, the team won. The whole run cost $1,620 at list price, by The Decoder's accounting.

Most coverage read this as "AI beats another video game," filed between chess and Go. That misses the actual result. Prior Minecraft agents were purpose-built systems — policies trained on gameplay, or language models bolted to game-specific planners, curricula, and skill libraries. These four were stock coding agents, the same ones engineers use for everyday software work, each on its own cloud machine with a shell, a version-controlled workspace, and persistent memory. The run is the first end-to-end autonomous completion of the game using only the standard Mineflayer bot library. What got demonstrated was not gaming skill. It was 27 hours of unattended goal persistence by general-purpose agents that failed constantly.

That reframing matters for anyone building agent systems, because the interesting engineering in this run is not in the programs. It is in what happened between them.

What Actually Ran

The mechanics are worth being precise about, because the architecture is the finding. Each agent controlled a player through Mineflayer, an open-source JavaScript library maintained by the volunteer PrismarineJS ecosystem. The agents never saw pixels and never pressed keys. They acted by writing a short program — walk to these coordinates and mine every iron ore within 16 blocks — running it, and reading the text that came back: position, health, inventory, or the error. Then they wrote the next one. The median program ran for 33.5 seconds. Over the full session, each player had a program executing only about 40% of the time; the rest went to reading results, thinking, and writing the next attempt.

Coordination happened through the game's own chat — 229 messages in total, roughly one message per twelve programs — and through a shared memory: a persistent notebook with a private part and a team part. When one agent died, the others recovered its items. Nobody assigned roles; the four divided the work themselves, kept shared notes of coordinates and lessons, and re-planned as the world pushed back. A fifth instance of the same agent, the Observer, watched the entire session as an independent witness for cheating and specification gaming.

For calibration: HowLongToBeat's median for a human player finishing Minecraft's main story is 45 hours, and the random-seed speedrun record is under seven minutes. A team of four on Easy difficulty, playing through programs rather than a screen, landed at 27 hours — and roughly 81 in-game days. Slow against specialists, trivially fast against the median human, and doing something neither does: running unattended overnight.

The Program Became Disposable

Here is the number that should reorganize how you think about long-horizon autonomy: 22%. Twenty-two percent of the 2,783 programs ended in an error, and the run succeeded anyway. The dragon fight alone killed the agents 69 times across nearly 14 hours. If your mental model of a successful long-running agent is "a brilliant plan executed cleanly," this run is the opposite: a pile of mostly-failing, seconds-long, throwaway actions whose aggregate converged on the goal.

Most people think the bottleneck at long horizons is planning intelligence — the model needs to think harder about what to do. The Minecraft run suggests the actual bottleneck is failure economics: making each attempt so cheap that error stops being an event and becomes a texture. A program that took 33 seconds to write and run and failed cost the team almost nothing. Six hundred and five deaths cost the team almost nothing — respawn, re-equip from shared stores, try again. The design that makes failure cheap is what buys endurance, not brilliance.

But cheap failure alone just produces fast thrashing. What turned 2,783 disposable programs into a win was the part that compounded: the notebook. The clearest example is the End, where the dragon lived. Between attempts — between deaths 1 and 69 — the agents inspected the dragon's internal state from the game API, down to its current behavior phase, and wrote down rules for the next attempt: never wait on the arrival platform; approach only while the dragon is perched; leave the End on purpose to reset it when it gets stuck. Seventeen and a half hours in, all four agents jumped into the void within six minutes of each other — deliberately, using the game's own death-respawn mechanics to force the stuck dragon to reset. That is not a planning triumph. That is institutional knowledge, accumulated one failure at a time in a format that survived every subsequent failure.

The breakthrough itself was a notebook entry. Around hour 21, one agent worked out that the ten crystals atop the obsidian pillars were healing the dragon to full health, and that no pickaxe was needed to reach them: stack dirt beside each pillar, punch the crystal, dig back down. The team then spent four hours and forty minutes executing that single insight, and the dragon died thirty-nine minutes after the last crystal fell. The programs were disposable. The observation was not.

What Survived the Compaction

Underneath the story sits a harness decision that deserves more attention than it will get. No context window holds 27 hours of execution. The agents compacted their context the same way they would for long software work, and their instructions told them to keep in memory what must survive a compaction: work in progress, next steps, hard-won state. That sentence is the entire art of long-horizon agent design in one clause. Everything the team learned about the dragon lived in the notebook precisely because it could not live in the context.

This is the layer I called harness engineering in Harness Engineering: The Complete Guide to Agent-First Software Development, and it is where the frontier is quietly moving. The model is fixed; the question is what you build around it — and for long-running agents, the single highest-leverage component is the memory and compaction policy. Not because memory is glamorous, but because it is the only mechanism that converts thousands of failing steps into progress instead of repetition. An agent that cannot survive its own context resets is an agent with a maximum useful task length, no matter how smart it is per step.

Note also how little coordination the run required: 229 messages across 27 hours. The shared notebook did most of the work that multi-agent architectures try to do with orchestration layers. State in a common place, updated as a side effect of work, beats message-passing ceremony — the same lesson every distributed-systems engineer relearns annually.

The Observer Was Not Decoration

Any claim of autonomous success invites the cheating question, and the DeepMind team answered it with the right instrument: total recording. Every program and its output, every chat message, periodic world snapshots, and the full server log — where the win itself is recorded, 27 hours 14 minutes after the first program. Cheat commands were disabled; no program issued a server command or made a network request — the agents had web search available and never touched it, settling the "did they just download a walkthrough" objection. The Observer, an independent instance of the same agent, watched for specification gaming throughout and found none, and the authors' manual audit of sampled logs agreed.

The transferable point is not "agents don't cheat." It is that autonomy is only credible at full telemetry. A 27-hour unattended run is exactly the kind of artifact an enterprise will be asked to trust, and the reason this one is quotable is that its proof lives in a server log rather than a press release. If your agent pipelines don't record every action, input, and output at this granularity, your autonomy claims are unfalsifiable — including to yourself.

Persistence Became a Product the Same Week

The timing is what makes this more than a game story. Days after the run circulated, Meta shipped Muse Wonder and Muse Wonder Full, built around two named capabilities: Active Memory (carrying important context across conversations and retrieving the relevant details) and Active Focus (continuing toward a goal through blockers, trying alternatives, adapting). The launch materials pitch exactly the properties the Minecraft run exercised — and Meta evaluates them with purpose-built tests: FocusBench for goal persistence, and SWE-Marathon for long-running software work.

Meta's own model-card numbers make the strategic split explicit. On SWE-Marathon, Muse Wonder Full scores 57.5 against 46.3 for Claude Opus 5.5 and 42.5 for GPT-6 Astra — an eleven-point lead in sustained execution. Yet on the Artificial Analysis composite index, Opus 5.5 still leads, 58 to 56. By Meta's own table, the more intelligent model in aggregate is the less persistent one on long-horizon work. Competitor runs were best-effort and the caveats are real, but the direction is unmistakable: the labs have stopped selling only intelligence per step and started selling time-on-task. Endurance is being unbundled from IQ and priced separately.

Read the two events together and a 2027 planning assumption falls out: the unit of agent work is becoming the day, not the turn. DeepMind demonstrated a day-long task completed by general-purpose agents; Meta productized the memory and focus that make it repeatable; the remaining gap — reliability across repeated runs, which a single first-launch attempt cannot show — is now the measurable frontier.

The Limitations That Matter

The authors are unusually direct about what the run does not prove, and the list should travel with the headline. The agents perceived the world through an API that tells them exactly which blocks and creatures surround them — including blocks behind solid rock and the dragon's internal phase state — with a pathfinding plugin planning their routes. A human has to see and interpret; the agents read ground truth. Playing from pixels, as DeepMind's own SIMA does, remains much harder. They played on Easy. Gemini 4 Argon also knows a great deal about Minecraft and Mineflayer from training data, so this tested turning knowledge into working programs, not learning a game cold. Six server restarts interrupted the world. And it is a single run — the first launch they tried — so it demonstrates possibility, not a success rate.

None of that dims the useful part. Enterprise work is also API-shaped: agents that act by writing code against systems that report state as text. Your production agent reading a dashboard API and a database is closer to Mineflayer than to pixels. The run's limitations define the next benchmarks — pixels, harder difficulty, repeated trials — while its architecture is available for copying today.

What to Do This Week

1. Write down your compaction survivors. For your longest-running agent task, list explicitly what must survive a context reset: in-flight state, next steps, learned constraints, resource locations. If that list lives nowhere, every long task your agents run is quietly capped by your context window. This is the single highest-leverage hour available to you.

2. Stand up the shared notebook before the second agent. If you run multi-agent work, replace ad-hoc message-passing with a common, structured memory that every agent updates as a side effect of working. The Minecraft team coordinated an entire 27-hour project on 229 messages because the notebook carried the rest.

3. Start measuring error economics, not error rates. Track the median cost of a failed attempt — time, tokens, dollars — and the time-to-recovery after failure. The 22% error rate was survivable because each failure cost 33 seconds. Your agents' error rate is only a problem insofar as failures are expensive; measure the denominator.

4. Record everything, server-log grade. Every program, every output, every message, one immutable log. The DeepMind team can prove a negative — no cheating — because nothing went unrecorded. Set that bar for your own autonomy claims before a regulator, a customer, or a postmortem sets it for you.

5. Run your own marathon. Pick one internal task that genuinely takes four or more hours. One paragraph of instructions, no human input, full recording, and a success criterion that lives in a log. Whether it succeeds or stalls, the artifact you get back — where it lost the thread, what it forgot, when it recovered — will teach you more about your harness than any benchmark chart.

The dragon was never the point. Four general-purpose agents held one goal across 2,783 mostly-failing programs, 605 respawns, and a night's worth of context resets, because everything worth keeping was written down. The programs were disposable. The notebook wasn't. That is what 27 hours of autonomy actually looks like — and it is now a copying license, not a research result.
